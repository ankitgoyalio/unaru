# Windows and presentation

Let people resize content windows and use native tiling and full screen. Choose minimum dimensions by the smallest useful content layout; a utility or fixed-format panel can have different constraints. System window chrome communicates close, minimize, zoom, and active/inactive state. Keep native controls functional, and let custom surfaces reflect the window state.

Open documents or independent tasks in multiple windows where it helps comparison and context. Keep window-specific selection, focus, undo, and draft state separate. Route each command to its intended context: text editing follows the first responder, while document actions use the associated document. A key panel can differ from the main document window; verify both cases rather than relying on a global last-opened document. Restore useful geometry and document state through the app's actual scene/document restoration support; a WindowGroup declaration alone is not proof that every state restores.

Close (Command-W) closes the current window or tab; Quit (Command-Q) terminates the app. In a document app, closing one document leaves other documents usable. Use native open/save and recent-document behavior. Document windows should expose the document identity and editing state through the document system, including represented file URLs where applicable. Window titles distinguish content rather than repeating the app name. Critical controls belong where they remain available if the bottom edge is offscreen.

Use a popover for transient options anchored to their source, an inspector for persistent contextual tools, and a sheet for a task attached to a particular window. Give cancellation and default actions their native keyboard behavior. Check keyboard entry, navigation, and Escape/Return, then return focus to the invoking control or a useful content target on dismissal. Reserve app-wide modality for decisions that truly block the whole app. Alerts explain a consequential choice or failure; routine success stays inline. Suppression is appropriate only for repeatable informational warnings whose later omission is safe.

Sources: [Windows](https://developer.apple.com/design/human-interface-guidelines/windows), [Toolbars](https://developer.apple.com/design/human-interface-guidelines/toolbars), [Popovers](https://developer.apple.com/design/human-interface-guidelines/popovers), [Sheets](https://developer.apple.com/design/human-interface-guidelines/sheets), [Alerts](https://developer.apple.com/design/human-interface-guidelines/alerts).
